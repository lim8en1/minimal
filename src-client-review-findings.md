## 1. Transport & RPC core

Paths reviewed: `session_client.{hpp,cpp}`, `rpc_queue.{hpp,cpp}`, `scrollback_refresh.{hpp,cpp}`.

1. **[correctness/leak]** `session_client.cpp:317` — `PluginSubscribe`'s declined/cancelled exit path (`on_payload` returns `false`, `kCancelled`) calls `TryCancel()` and erases the context from the registry, but never calls `reader->Finish()`, unlike the normal-completion path (:326). gRPC's sync streaming API requires `Finish()` on every call to release the call object; every routine unsubscribe (a plugin's own retry-on-error logic) leaks the call's resources, accumulating over a long TUI session with active plugins that resubscribe repeatedly.
2. **[correctness]** `session_client.cpp:608` — `Stream::Open()`'s resume branch sends only `session_id`/`run_mode`, silently dropping `CreateOptions::model`/`CreateOptions::signals` — both documented as "sent either way" and applied on resume server-side (`session_service.cpp:461-483`), and both sent unconditionally by the parallel headless path (`SessionClient::CreateSession()`, :93-98). Currently dormant since `AppState::ResumeTab` doesn't populate those fields, but a future caller relying on the documented contract would have its override silently discarded on the TUI resume path only.
3. **[cleanup]** `scrollback_refresh.cpp:68` — `ScrollbackRefreshState::refresh_from_version` is written on every submit (`AdvanceScrollbackRefresh`) but never read anywhere in the tree; `AppState::RequestScrollback` (state.cpp:3244) independently recomputes its own submit-time snapshot instead of consuming it. Dead write-only state — a future refactor could assume it gates something when it does nothing.
4. **[cleanup]** `session_client.cpp:799-833` — `Detach()`'s bounded-join logic for the writer and reader threads is duplicated near-verbatim (timeout computation, `wait_until`, cancel-then-wait-again fallback), differing only in which thread/cv/flag is used. Both copies must stay in lockstep to preserve the 2s Detach()-doesn't-hang-quit guarantee; a fix applied to one and not the other silently reintroduces the asymmetry this code exists to avoid.

Cross-subsystem notes: none flagged.

## 2. Session & app state

Paths reviewed: `state.{hpp,cpp}`, `chat_model.{hpp,cpp}`, `status_format.{hpp,cpp}` — full-file audit.

1. **[correctness]** `state.cpp:731` — `live_view_truncated_` only resets on the full live-segment-clear branch, not on the partial-retirement path in `ClearStreamingIfCurrentTurn`/`RetireCoveredLiveSegments`. A turn that overflows `kMaxLiveSegments` (latch set) followed by a next turn whose retirement takes the partial branch (some segments survive because they belong to the newer turn) never resets the flag, so the status bar's "hidden rows" notice can outlive the turn that caused it — broader than what the header doc comments (state.hpp ~368-373, ~1000) claim ("until the turn-end refresh retires the covered segments").
2. **[correctness]** `state.cpp:1136` — `OnToolStarted`'s redelivery guard only checks `existing.started == true`, so a "started" event redelivered for a `tool_use_id` *after* that tool already finished (`started == false`) isn't recognized as a duplicate. A late-arriving started replay with no matching redelivered finish pushes a phantom row that never gets `OnToolFinished`, so `MaybeGoIdleLocked()` never sees `tool_active` go false — the tab is permanently stranded "Working" with a ghost row in the tools panel, the exact failure the guard exists to prevent, just not for this arrival ordering.
3. **[correctness]** `chat_model.cpp:128` — `InputSummary()` truncates JSON-dumped tool input with a plain byte-oriented `substr(0,120)` instead of the codebase's own UTF8-aware `TruncateUtf8` (used by every other truncation site: `OneLineSummary`, `AppendStreamingText`, `OnToolOutputDelta`). A multi-byte UTF-8 character near byte 120 (non-ASCII path/commit message/arg) gets cut mid-sequence, and the result is consumed unguarded at `plugins/core_registrations.cpp:363`, landing invalid UTF-8 in the persisted `ToolActivity` row header.
4. **[correctness/concurrency]** `state.hpp:1534` — `chat_surface_` is a plain (non-atomic) raw pointer written by `SetChatSurface()` and read on every reader thread via `DispatchToTab` (state.cpp:2157), with no synchronization or documented single-init-before-threads guarantee — unlike its sibling `chat_surface_broken_` (made `std::atomic<bool>` specifically to fix a TSan-visible unsynchronized race) and `plugin_attention_` (whose setter explicitly documents "called once before any reader thread exists"). If `SetChatSurface()` is ever called after a tab's reader thread is running (e.g. late/dynamic plugin registration), the unsynchronized write races concurrent reads — a torn/stale pointer read is UB, the same bug class already fixed one field below it.
5. **[correctness]** `chat_model.cpp:229` — `SelectRowWindow`'s `force_include` loop extends `first`/`last` without checking `spans[included].known()`, unlike the intersection-scan loop immediately above it, which explicitly skips unknown spans. A force-included row that's never been laid out (e.g. the just-toggled row) can be the "never laid out" sentinel (`y_min=0, y_max=-1`), silently undercounting elided space above or overcounting it below by 2 — distorts the scroll-filler height relative to FTXUI's actual layout, causing scroll-offset drift.
6. **[design]** `state.cpp:1735` — `~AppState()` calls only `CloseAllTabs()`, never `StopRpcQueue()`, though `StopRpcQueue()`'s own doc comment (state.hpp ~1417) says it must run "BEFORE `CloseAllTabs()`" because a queued RPC job's completion callback touches state the same way a reader-thread dispatch does. If an `AppState` falls out of scope without an explicit prior `StopRpcQueue()` call (exception path, early return), the destructor may race a still-running/queuing RPC job against concurrent teardown. Not independently confirmed without `RpcQueue`'s own destructor semantics — flagged as a documented-ordering gap, not a confirmed crash.
7. **[cleanup]** `state.cpp:363` — Stale comment in `AppendStreamingText` still describes the removed `"[...truncated]"` marker / `turn_seq 0` sentinel design (`e6f9f03` deleted it); `TrimLiveSegmentsLocked` no longer creates any marker or stamps `turn_seq 0`. A maintainer reading this comment will assume a synthetic marker segment still exists.
8. **[cleanup]** `state.cpp:720` — The 6-line "clear all streaming state" block (`streaming_accumulated_`/`streaming_truncated_`/`thinking_accumulated_`/`thinking_truncated_`/`is_streaming_`/`live_segments_`/`live_view_truncated_`) is duplicated verbatim across five sites: `ClearStreaming()` (720-729), `ClearStreamingIfCurrentTurn`'s "nothing survives" branch (744-753), `RetireCoveredLiveSegments`'s "everything retired" branch (833-843), `OnResyncRequired` (975-981), `OnSessionRewound` (1037-1043). A field add/rename requires updating all five by hand; a missed site reproduces the state-drift bug class this file has chased before. A private `ClearStreamingLocked()` helper would remove the risk.

## 8. Client plugins (host)

Paths reviewed: `plugins/plugin_loader.{hpp,cpp}`, `plugin_discovery.{hpp,cpp}`, `registries.{hpp,cpp}`, `core_registrations.cpp`, `core_display_renderers.cpp`, `host_seams.{hpp,cpp}`, `client_plugin_abi.h` — full-file audit.
